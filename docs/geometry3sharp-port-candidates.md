# Geometry3Sharp algorithms and data structures worth porting to Plato

**Assessment date:** 2026-07-12  
**Scope:** Geometry3Sharp `master` and its documented public surface, compared with the current Plato production library and compiler/runtime capabilities in this repository. The existing bridge consumes NuGet package `geometry3Sharp` 1.0.324.

## Executive recommendation

Do not attempt a broad source port. The highest return is a staged, behavior-oriented port of Geometry3Sharp's pure query kernels, followed by immutable spatial indexes and selected mesh analysis algorithms. These fit Plato's pure value model, strengthen the existing `TriangleMesh3D` API, and become portable across C#, TypeScript, Rust, and future targets.

The best first portfolio is:

1. Closest-point, distance, and intersection kernels for Plato's existing primitives.
2. `Option<T>` / `Result<T,E>`, tolerances, and robust 2D orientation predicates needed to expose those kernels honestly.
3. Mesh measurements, normals, adjacency, connected components, and boundary-loop extraction over indexed triangle meshes.
4. An immutable, array-backed triangle AABB tree with ray-hit and nearest-point queries.
5. Only then, evaluate QEM reduction and plane cutting—the two expensive Geometry3Sharp features already used by `G3SharpBridge`.

Avoid beginning with `DMesh3`, remeshing, mesh repair, mesh booleans, file I/O, or the full numerical-solver stack. Those are valuable systems, but their mutable object graphs, sparse ID management, callbacks, and failure modes fight Plato's current strengths and would force runtime/compiler design before delivering geometry value.

## Evidence and assessment method

Geometry3Sharp describes itself as a Boost-licensed geometric-computing library. Its catalog spans low-level distance/intersection queries, dynamic meshes, mesh editing and repair, generators, AABB trees and grids, curves, computational geometry, and numerical solvers ([upstream repository and class catalog](https://github.com/gradientspace/geometry3Sharp)). The upstream README also says a modern `.NET 8` update is under active development on a separate branch, so names and implementations should be rechecked before any direct port begins.

Local evidence:

- [`G3SharpBridge.cs`](../submodules/Plato.Geometry/Plato.Geometry.G3Sharp/G3SharpBridge.cs) currently depends on `DMesh3`, `DMeshAABBTree3`, nearest-point/ray queries, `MeshPlaneCut`, `Reducer`, mesh constraints, projection targets, and mesh I/O.
- [`Plato.Geometry.G3Sharp.csproj`](../submodules/Plato.Geometry/Plato.Geometry.G3Sharp/Plato.Geometry.G3Sharp.csproj) pins package version 1.0.324.
- Plato already has immutable point, line, ray, triangle, bounds, polyline, grid, and indexed mesh types; functional arrays; scalar fields and SDF primitives; and runtime-checked affine `List<T>` / `Buffer<T>` builders.
- Plato remains pure at the language level: no I/O, exceptions, or unrestricted mutation. General mutable maps/sets, sparse-index containers, and a production dynamic-topology mesh are not present.
- A convex-quad ear-clipping slice and triangle-extrusion slice already exist as affine-builder validation tests. They are proofs, not general production triangulation/extrusion implementations, and should not be counted as completed ports.

Ratings use four priorities:

- **P0 — port first:** foundational, high reuse, and a strong Plato fit.
- **P1 — next:** high product value after small or known prerequisites.
- **P2 — later:** useful but architecturally substantial or narrower in payoff.
- **Defer:** poor fit today, duplicated elsewhere, or too risky for the expected return.

Effort is relative and includes Plato API design and differential tests, not just transliteration.

## Recommended dependency sequence

| Stage | Deliverable | Enables |
|---|---|---|
| 0 | `Option` / `Result`, tolerance policy, finite/degeneracy conventions | Honest portable APIs for every query and iterative algorithm |
| 1 | Primitive closest-point, distance, intersection, bounds, robust 2D predicates | Spatial trees, polygons, triangulation, cutting, measurements |
| 2 | Sorted-edge mesh adjacency plus selection/components/boundary loops | Normals, mesh weights, smoothing, cutting, simplification |
| 3 | Flat immutable triangle AABB tree | Fast picking, nearest point, projection, ICP, SDF, broad-phase intersection |
| 4 | Mesh analysis: measurements, normals, weights, curve sampling, polygons | Immediate Studio-facing geometry capability |
| 5 | Dense grids + deterministic Marching Cubes | Plato SDF-to-mesh pipeline |
| 6 | One topology-changing vertical slice: either QEM reduction or plane cut | Validates whether operation-specific affine workspaces suffice |
| 7 | Only if justified: reusable dynamic topology, heap/hash runtime intrinsics, sparse grids/solvers | Remeshing, generalized repair, high-end mesh processing |

## Suggested first three port milestones

### Milestone A — query kernel

Implement a compact `queries2d.plato` / `queries3d.plato` surface covering point–segment, point–triangle, segment–segment, ray–triangle, and ray–AABB. Define result records such as `RayHit3D` and `ClosestPoint3D`, with `Option` for no-hit results. Differential-test seeded, degenerate, parallel, and near-boundary inputs against Geometry3Sharp 1.0.324 and analytic witnesses.

### Milestone B — immutable mesh analysis

Build sorted undirected edge records from `TriangleMesh3D.FaceIndices`, group them to derive triangle neighbors and boundary edges, then add connected components, boundary loops/spans, face/vertex normals, surface area, signed volume, and centroid. This delivers substantial value without taking on `DMesh3` mutation.

### Milestone C — flat AABB tree

Construct a binary BVH into affine buffers and freeze it into flat arrays. Ship nearest-triangle/nearest-point and nearest ray-hit queries first. Compare correctness against `DMeshAABBTree3` and benchmark construction/query throughput on representative Studio meshes. Dynamic updates, winding number, tree/tree intersections, and fast winding remain later extensions.

## API and implementation guidance

- **Port behavior, not class hierarchy.** Geometry3Sharp is object-oriented and mutation-oriented; Plato should expose small immutable records and free functions.
- **Prefer arrays of records or structure-of-arrays layouts.** Flat storage maps cleanly to C#, TypeScript, Rust, and WASM and works with Plato's affine builders.
- **Keep construction separate from queries.** For example, an AABB tree may use affine mutation while building, then become an immutable query value.
- **State preconditions in types/results.** Closed/oriented/manifold requirements should be validated or represented, not assumed silently.
- **Make deterministic single-threaded behavior normative.** Backends may later parallelize construction or bulk queries without changing results.
- **Use differential tests selectively.** Geometry3Sharp is an excellent oracle for mainstream cases, but upstream issues and the README's warnings mean it should not be treated as proof of robustness. Analytic properties and adversarial degeneracy tests remain necessary.
- **Preserve licensing provenance.** Geometry3Sharp is BSL-1.0, and parts are credited to Geometric Tools/GTEngine and SDFGen. If code is translated directly, retain required notices and source-level attribution. For compact standard algorithms, a fresh implementation from the underlying paper/specification can yield a cleaner Plato-native design while still documenting inspiration.

## Bottom line

The strongest Geometry3Sharp contribution to Plato is not its complete dynamic-mesh architecture; it is the well-proven ladder of geometric kernels and acceleration interfaces underneath it. Porting that ladder in dependency order gives Plato a coherent computational-geometry foundation while preserving its pure, multi-target identity. The decision point for a true dynamic topology subsystem should come only after one real simplifier or cutter demonstrates that immutable meshes plus affine operation workspaces are inadequate.
